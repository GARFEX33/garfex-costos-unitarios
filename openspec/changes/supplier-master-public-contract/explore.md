# Exploration: `supplier-master-public-contract` — public contract for the Supplier Master module

## Current State

**`resourcecore` — the pattern being mirrored** (repo root, 16 files: `reader.go`, `writer.go`, `types.go`, `write_types.go`, `queries.go`, `values.go`, `errors.go`, `copy.go`, `doc.go` + tests):
- **Reader** (`resourcecore/reader.go`): `ReadCapabilities` interface (7 methods: `ActiveClasses`, `CatalogDescriptors`, `ListCatalog`, `GetCatalog`, `SearchResources`, `GetResource`, `DescribeResource`) + public `Reader` struct wrapping it. `NewReadOnly(cap ReadCapabilities) (*Reader, error)` rejects nil. Every method validates request shape (`validateCatalogQuery`, `validateResourceKey`, etc.) then delegates, then defensively clones every returned mutable collection (`cloneCatalogRecordSlice`, `CloneResource`, ...).
- **Writer** (`resourcecore/writer.go` + `write_types.go`): `WriteCapabilities` interface, now 9 methods after 4 sequential SDD changes — `CreateCatalog/CreateResource/UpdateCatalog/UpdateResource/DeactivateCatalog/ReactivateCatalog/DeactivateResource/ReactivateResource/HardDeleteCatalog`. Public `Writer` struct: shape-only validation (`validate*Request` free functions using `strings.TrimSpace`/zero checks), delegates to `cap`, clones both the outbound request and the inbound record via `Clone*` helpers. Request types (`CatalogWriteRequest`, `ResourceWriteRequest`, `*UpdateRequest`, `*LifecycleRequest`) all carry an `Actor string` field, and lifecycle/update requests all carry `ExpectedRevision uint64` for optimistic-concurrency CAS.
- **`resourcecore/writer_test.go:216` `TestWriter_NoUngraduatedMethodExported`** — a reflection-based exhaustive compiled-surface guard: asserts `WriteCapabilities` has exactly N methods with exact names, and that `Writer`'s exported method set is a subset of that allow-list. This is the mechanism that made `HardDeleteResource` a *provable* gap rather than an oversight — every graduation PR updates this assertion.
- **`resourcecore/doc.go`** states the package contract explicitly: a translation boundary over `internal/app/catalogo.Service` and `internal/app/recursos.Service` via a bridge; owns its own DTOs; never aliases internal domain values; "the presence of this package's read API is never permission to infer that any write operation is available."
- **Bridge**: `internal/bridge/resourcecore/adapter.go` — `Adapter` implements both `public.ReadCapabilities` and `public.WriteCapabilities` (`var _ public.ReadCapabilities = (*Adapter)(nil)`), composed from two narrow internal seam interfaces per aggregate (`catalogReader`/`catalogWriter`, `resourceReader`/`resourceWriter`), constructed via `NewAdapter(catalog catalogPort, resources resourcePort)`. It does field-mapping/type-translation only — "the bridge translates, it does not re-implement" (explicit guardrail added to the harddelete proposal to prevent a second, drifting rule implementation).
- **Critical fact confirmed by direct evidence, not assumption**: `resourcecore.NewWriter` **has no production composition root today**. `Grep` for `resourcecore.NewWriter`/`resourcecore.NewAdapter` outside tests returns nothing; `Glob cmd/**` returns no files. The harddelete proposal (archived same day) still referenced `cmd/garfex/main.go:66` as the production reach point, but `c38aacf "chore(architecture): remove TUI and CLI interface layer"` landed after that archival and deleted `cmd/`. So today `resourcecore`'s Reader and Writer are fully built, tested public contracts that **nothing in this repo actually constructs** — they exist purely as the library surface a future UI will import. This is the accurate mental model for "any UI can use it," not "a UI is currently wired to it."

**`internal/modules/suppliers` — the module to graduate**:
- `domain/supplier.go`, `domain/branch.go`, `domain/contact.go`: three structs — `Supplier{ID, TradeName, LegalName, TaxIdentifier, Website, Notes, Active, CreatedAt, UpdatedAt}`, `Branch{ID, SupplierID, Name, Reference, City, State, Country, Address, GeneralPhone, GeneralEmail, Notes, Active, ...}`, `Contact{ID, SupplierID, BranchID *int64, Name, Role, Phone, Mobile, Email, Notes, Active, ...}`. Each has a paired `*Details` struct (no ID/Active/timestamps) plus `NewX`/`WithDetails` constructors that trim and validate. **None of the three has a `Revision` field** — there is no optimistic-concurrency/CAS concept anywhere in this module.
- `domain/repository.go`: single `Repository` interface, 15 methods, covering Supplier + Branch + Contact CRUD/lifecycle as one cohesive port. `SetSupplierActive`/`SetBranchActive`/`SetContactActive` are boolean toggles, not CAS-guarded transitions — no `ExpectedRevision` parameter anywhere.
- `app/service.go` + `supplier.go`/`branch.go`/`contact.go`: `Service{repo domain.Repository}`. Supplier ops named `CreateSupplier/GetSupplier/SearchSuppliers/UpdateSupplier/DeactivateSupplier/ReactivateSupplier`. Branch/Contact ops named `AddBranch/AddContact` (not `CreateBranch/CreateContact` — inconsistent with both Supplier's own naming and resourcecore's `Create*` convention) plus `Get/List/Update/Deactivate/Reactivate`. `AddContact` and `UpdateContact` both call `ensureBranchOwnership` — a cross-entity invariant (a contact's `BranchID`, if set, must belong to the same `SupplierID`) that has no analogue in resourcecore's Catalog/Resource duality.
- `postgres/`: one `repository` struct implementing all 15 methods against three Postgres tables (`supplier_branches`, `supplier_contacts`, presumably a `suppliers` table).
- `module.go`: `Module{Service *app.Service; Repository domain.Repository}`, built by `New(pool *pgxpool.Pool)`. `NewService` has 7-8 callers, all either tests or `internal/app/catalogo/service.go` / `internal/app/recursos/service.go` — i.e., **other internal application services depend on the suppliers `Service` directly today**, not through any port/adapter boundary. This is the equivalent bridge point resourcecore's `internal/bridge/resourcecore/adapter.go` occupies, except for suppliers **no such adapter exists yet** — `catalogo.Service` and `recursos.Service` hold a direct reference to `*app.Service` (the internal suppliers service), not to an interface a bridge could substitute.
- `domain/errors.go`: a small, informal error taxonomy — `ErrValidation`, `ErrNotFound`, `ErrConflict` sentinels, three `*NotFound` wraps, `ErrTaxIdentifierConflict`, `ErrBranchOwnership`, and a `ValidationError{Field, Message}` struct with `Unwrap() error`. This is materially simpler than resourcecore's formal `Error`/`ErrorCode` type with 15 stable categories and `IsCode()`.
- **No `Actor` concept anywhere in the module** (`Grep "Actor|WithActor"` under `internal/modules/suppliers` returns zero matches) — unlike resourcecore, where every write request carries `Actor string` fed through `core.WithActor(ctx, ...)` for diagnostic-only attribution.
- **No HardDelete anywhere** for Supplier, Branch, or Contact (confirmed: `Grep "HardDelete.*Supplier"` matches nothing in this module) — this is a *total* absence, not the catalog-only carve-out resourcecore has for `HardDeleteResource`.

## Affected Areas (for a future proposal/design/tasks phase, not touched by this exploration)

- `resourcecore/reader.go`, `writer.go`, `write_types.go`, `types.go`, `doc.go`, `copy.go` — read as the exact pattern to mirror or deliberately diverge from.
- `internal/bridge/resourcecore/adapter.go` — read as the bridge pattern; a new `internal/bridge/suppliercore/adapter.go` (or similar) would be the equivalent seam.
- `internal/modules/suppliers/domain/{supplier,branch,contact,repository,errors}.go` — the internal capability surface a public contract may only mirror, never exceed.
- `internal/modules/suppliers/app/{service,supplier,branch,contact}.go` — the internal `Service` a bridge would wrap; note it is consumed directly (no interface) by `internal/app/catalogo/service.go` and `internal/app/recursos/service.go` today, so introducing a bridge does not remove that direct dependency, it only adds a second, parallel public-facing path.
- `internal/modules/suppliers/module.go` — composition root pattern (`New(pool) Module`) to mirror for wiring a future bridge adapter, if one is added.
- No `cmd/` composition root exists to actually wire either `resourcecore` or a hypothetical `suppliercore` into a running process — both would ship as library-only contracts until a UI module is added to this workspace or a consuming repository imports them.

## Approaches

1. **Single change, full Reader+Writer, all three entities (Supplier+Branch+Contact) at once**
   - Pros: one cohesive `suppliercore` package shipped complete; avoids repo-wide asymmetric "Supplier has a public contract but Branch/Contact don't" state; matches the fact that `domain.Repository` already treats the three as one port.
   - Cons: large surface for one SDD change — likely blows the 400-line review budget (15+ repository methods × request/record types × validation × bridge translation × reflection guard tests); mixes read-only risk (low) with CAS/Actor design decisions (higher, needs `sdd-design`) in one slice; resourcecore's own precedent explicitly rejected this shape (it did Read, then 4 separate Write slices).
   - Effort: High.

2. **Supplier-first incremental graduation, mirroring resourcecore's exact sequencing (Reader, then Create, then Update, then Lifecycle) — Branch/Contact deferred**
   - Pros: directly reuses the proven resourcecore playbook; each slice stays reviewable; each slice can independently resolve its own open design questions (Actor? Revision/CAS?) without blocking the others; matches the "no HardDelete" reality cleanly (there is simply no HardDelete slice, ever, unless product later adds the capability).
   - Cons: Branch/Contact stay internal-only for several more changes, so "any UI can use it" is not true for the full module until the series completes; risks the same scope-boundary confusion the harddelete proposal had to explicitly guard against ("Supplier has a public contract" could be misread as "Supplier Master has a public contract").
   - Effort: Low per slice, Medium-High for the full series.

3. **Reader-only first change covering all three entities (Supplier+Branch+Contact), Writer graduated later per-operation**
   - Pros: Reader has no CAS/Actor/authorization ambiguity (resourcecore's own Reader shipped first for the same reason); giving a UI read access to Branch/Contact immediately is lower risk than any write path; keeps the follow-on Writer series' scope small and focused since Reader's request/record shapes are already settled; reads (`GetSupplier`, `SearchSuppliers`, `ListBranches`, `ListContacts`, `GetBranch`, `GetContact`) have no cross-entity invariant to encode (only `ensureBranchOwnership` is a *write*-side rule).
   - Cons: still needs an explicit scope-boundary decision about whether "Reader" is one big change or three (Supplier/Branch/Contact) — the parent-scoped IDs (`GetBranch(ctx, supplierID, branchID)`) mean every Branch/Contact read DTO must carry `SupplierID` explicitly, which has no resourcecore analogue (Catalog/Resource are not parent-scoped).
   - Effort: Medium (one change) or Low×3 (three changes).

## Recommendation

Approach 3 (Reader-only first, covering all three entities in one change since reads carry no CAS/Actor ambiguity and Branch/Contact reads have no cross-entity invariant), followed by a Supplier-first Writer series patterned on Approach 2's sequencing (Create → Update → Lifecycle, no HardDelete slice ever, since no internal HardDelete capability exists for any of the three entities) — Branch/Contact writes as their own later slices once Supplier's Writer establishes the Actor/CAS design answers. Do not attempt Approach 1: resourcecore's own explore/proposal artifacts already demonstrate why a combined Read+Write, multi-entity slice for this pattern is oversized, and this module adds *more* open questions (Actor concept does not exist; CAS/Revision does not exist) than resourcecore had at its own first Writer slice.

This is a recommendation for the *proposal* phase to accept or reject — it is not binding, and the open questions below must be surfaced to the user before `sdd-propose` commits to any of it.

## Risks

- **No production composition root exists for either contract.** `resourcecore` (the precedent) has zero real consumers today; a new `suppliercore` will be in the identical position. If the user's actual goal is "wire a UI now," this exploration and any resulting SDD series only produces the library surface, not a running consumer — worth confirming expectations before proposing.
- **Actor field**: resourcecore's every write request carries `Actor string` (diagnostic-only). Suppliers has zero actor-attribution concept internally. Inventing an `Actor` field on `suppliercore` write requests would be adding a concept the internal capability does not have, not merely mirroring it — a genuine design decision, not a mechanical copy.
- **No CAS/Revision anywhere in suppliers.** resourcecore requires `ExpectedRevision` on every Update/Lifecycle request. Suppliers' `UpdateSupplier`/`SetSupplierActive`/etc. take no revision and are exposed to lost-update races today. A public write contract can either (a) match current internal capability exactly (no CAS, accept the race, and say so explicitly in `doc.go`-equivalent), or (b) treat adding revision-based CAS as new internal scope before any public write graduation — this is a bigger, cross-layer decision the explore phase must not resolve.
- **Parent-scoped IDs**: Branch/Contact are `SupplierID`-scoped, unlike resourcecore's independent Catalog/Resource aggregates. Every Branch/Contact request/record DTO must carry `SupplierID` (and Contact optionally `BranchID`), and `ensureBranchOwnership`'s cross-entity invariant needs an explicit home — either re-validated at the bridge (violating "the bridge translates, it does not re-implement") or left entirely to the internal service (meaning the public `Writer`'s shape-only validation cannot catch a foreign-branch contact before the round-trip).
- **`AddBranch`/`AddContact` vs `CreateSupplier` naming inconsistency** inside the app layer itself — a public contract copying resourcecore's `Create*` convention would need to decide whether to normalize this naming or carry the inconsistency forward.
- **No HardDelete anywhere in this module** (total, not catalog-only) — the public contract should almost certainly omit it entirely rather than inventing a capability the Core does not have; resourcecore's own explicit precedent (`HardDeleteResource` deliberately out of scope, proven by a reflection-based compiled-surface test) is the right model to cite when proposing this.
- **Direct internal coupling today**: `catalogo.Service`/`recursos.Service` hold a concrete `*app.Service` (suppliers), not an interface — adding a bridge does not remove or replace that coupling, it only adds a second path; scope this explicitly so the proposal doesn't imply an internal refactor that isn't actually needed.
- **Smaller, informal error taxonomy** (`ErrValidation`/`ErrNotFound`/`ErrConflict` + `ValidationError`) vs resourcecore's formal 15-category `Error`/`ErrorCode` — the proposal phase must decide whether `suppliercore` invents its own smaller `Error`/`ErrorCode` type (proportional to what 3 simple entities actually need) or mirrors resourcecore's fixed-at-15 pattern (over-engineered for this module's actual error surface today).

## Ready for Proposal

Yes, with explicit open questions the proposal phase must put to the user rather than resolve unilaterally:
1. Reader-first-all-three-entities vs. Supplier-first-everything (recommendation above is Reader-first-all-three, but this is a product/sequencing choice).
2. Whether `Actor` gets invented as a new public-only concept or omitted to exactly match current internal capability.
3. Whether adding CAS/`Revision` to Supplier/Branch/Contact is in scope for this series at all, or explicitly deferred with the public contract accepting the same lost-update race the internal service has today.
4. Whether the public error taxonomy is a small purpose-built `Error`/`ErrorCode` type or mirrors resourcecore's fixed-15 pattern.
5. Whether `ensureBranchOwnership` is re-validated at the bridge or left entirely internal (affects whether the public `Writer`'s shape-only validation can catch a foreign-branch contact).
